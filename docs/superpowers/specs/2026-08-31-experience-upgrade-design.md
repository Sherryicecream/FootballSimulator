# 体验升级设计：从月度模拟到可感知的足球生涯

状态：已获批准，按模块顺序实施。

## 背景

当前 M7 已完成 16 岁青训到退役回顾的生涯闭环，但体验层仍偏向“状态模块 + 文字选项”：选择之后缺少角色的即时回应，月份之间的推进缺少短期目标和转折，视觉信息层级与足球场景感也不足。

## 用户目标

玩家每次做出选择后，都能立刻理解三件事：现场发生了什么、谁对这个选择作出了回应、这会怎样影响接下来的训练/比赛/关系。玩家还应在一个月内看到可感知的过程，在几个关键月份遇到有上下文的转折，而不是只等待数字变化。

## 已确认的模块顺序

1. 事件即时反馈：先补齐“选择—回应—后续影响”的反馈闭环。
2. 生涯节奏：在月度流程内提高可感知事件密度与转折，不引入周推进或快进。
3. 视觉表现：统一图标、场景、标题层级、状态徽章和响应式布局。
4. 内容与 AI：扩充有事实依据的事件链和人物对话变体，再审慎引入本地 AI 辅助内容。

## 模块 1 的产品规则

- 只有玩家主动选择的交互事件需要停留在反馈页；自动事件继续无感完成。
- 反馈至少包含现场结果、参与人物回应、实际状态/关系变化和后续影响。
- 反馈写入存档，刷新后恢复；点击“继续推进”才解除暂停。
- 未确认反馈不能推进青训月份、职业月份、休赛期或阶段结束。
- 所有反馈来自显式事件内容、参与人物和已经结算的 ledger/state，不使用不可复现的外部生成结果。

## 非目标

- 本轮不把全部历史事件做成静态剧情图鉴。
- 本轮不改变 M7 的职业规则、合同阶梯和阶段机。
- 本轮不在 web 组件内复制 simulation 规则。
- 本轮不让核心模拟依赖网络 AI 服务。

## 验收方式

- 每个模块先增加失败回归测试，再实现行为。
- 每个模块完成后运行完整测试、类型/Lint/格式/构建、桌面与移动 E2E，以及规定的 1,000 赛季平衡命令。
- 每个模块完成后向用户汇报并提供本地运行版本；未完成模块不提前宣称已解决。

## 模块 3：视觉与场景表现设计

### 目标

将核心循环从“状态模块 + 文字列表”提升为可识别的足球生涯工作台：玩家能快速看出当前处于训练、比赛、恢复还是关系事件，同时保留完整文字信息和实际数值。视觉层优先服务月度仪表盘、事件选择和事件反馈三个连续界面。

### 视觉方向

- 延续现有深色底色，以球场绿、荧光黄作为主强调色，以琥珀、红色区分警告和风险；标题使用高对比的显示层级，正文保持可读的中性色。
- 使用 CSS 设计令牌统一颜色、间距、圆角、阴影和字号；不再让核心事件页依赖分散的内联样式。
- 使用轻量、语义化的内联 SVG 图标表示训练、比赛、体能、疲劳、士气、状态、教练评价和关系；图标旁始终保留文字，不以图标替代信息。
- 使用 CSS/SVG 场景条表达训练场、比赛日、更衣室和恢复状态。场景由 application 已输出的月度节奏或事件主题驱动，不能在 web 中重新推断模拟规则。

### 组件与数据边界

- `design-system/tokens.css` 提供全局视觉令牌；`app.css` 只负责布局、响应式和组件皮肤。
- 新的场景、图标和状态徽章组件只接收已格式化的展示数据或明确的语义枚举，不读取随机源、账本或保存对象内部规则。
- `CareerDashboard`、`ProDashboard`、`EventChoicePanel`、`EventFeedbackPanel` 复用相同的标题、卡片、徽章和场景组件；青年/职业差异只来自 application 输出。
- 旧存档缺失视觉辅助字段时，组件使用稳定的中性场景和现有文字，不阻断加载。

### 可用性与响应式

- 桌面端保持核心信息的分栏层级，移动端改为单列流式布局，不能出现横向滚动。
- 颜色不是唯一状态信号；风险、伤病和变化同时使用文字或图标说明。
- 所有交互控件保留可见焦点、键盘操作和现有 aria-label；场景装饰使用 `aria-hidden`，语义文本仍由页面结构提供。

### 非目标

- 不引入大型 UI 框架或外部图标服务。
- 不引入生成式图片作为核心运行时依赖，不改变 simulation/application 的业务规则。
- 不在本模块扩充事件数量、人物对话或本地 AI 内容；这些属于模块 4。

### 模块 3 验收

- 设计令牌、图标、状态徽章和场景组件有独立组件测试。
- 青训、职业、事件选择和事件反馈的核心页面有桌面/移动端可见性 E2E 断言。
- 生产构建、格式、类型、Lint 和无横向溢出检查通过；模块完成后仍执行完整回归和 1,000 赛季平衡命令。
