# 重要比赛交互关键时刻设计（M10 模块 8）

> 日期：2026-09-05

## 1. 目标

补齐 MVP 完成定义中唯一未达成的第 4 条：重要比赛具有位置专属关键时刻，玩家选择行动意图，结果由能力、状态与受控随机共同决定（复用 M10 模块 1 的三档判定）。普通比赛保持自动结算，不受影响。

## 2. 设计决策

### 2.1 重要比赛判定

- 职业期：国内杯八队三轮淘汰赛整体天然重要（`competitionId === 'domestic-cup'`）；联赛对手强度 ≥ 82 亦计。
- 青训期：联赛对手强度 ≥ 82 的比赛（青训机构强度分布 64–84，仅顶尖青训对话达标）。
- 每赛季重要比赛数量按判定自然落在 spec §8 的 0–4 区间，由平衡报告验证；不设人为配额。

### 2.2 关键时刻建模

- 每场重要比赛在球员实际出场（`minutesPlayed > 0`）后，产生**一个**交互关键时刻（spec 区间 1–3 的下界；自动风味时刻后续扩展）。
- 关键时刻复用事件系统：以 `pendingEvent` 承载（`storyId: 'match-moment'`），携带比赛事实引用与对手强度；由此免费获得原子提交、读档恢复、反馈持久化与月度交互上限（每月 ≤2）。
- 选项为 3 个**位置专属行动意图**（前锋/边锋/中场/边卫/中卫各一套），每个选项带 M10 模块 1 三档 `resolution`（属性、难度、成功/部分/受挫）。
- 结果语义：比赛结果已在周模拟中固定，关键时刻决定球员的**个人表现叙事**（成功 = 高光贡献；受挫 = 陷入困境），并小幅影响信心/教练评价/士气（±1~3）与人物记忆。文案与比分/胜负一致（胜/平/负各有语气），不回改比赛结果与已产生数据。

### 2.3 触发时机

- 月度推进循环内、当周转移完成后、常规事件抽取之前检查：本周存在重要比赛事实且球员出场、当前无待决关键时刻 → 生成并打断。
- 随机源使用 `seed + 9100 + 周键哈希` 派生，仅用于"本周是否生成时刻"的抑制度（避免每个强敌场次都打断），选项内容为确定性的位置映射。
- 读档恢复：待决时刻随 `pendingEvent` 持久化；重入月度推进不重复生成。

### 2.4 分层归属

- 契约：`MatchMomentChoiceId` 无需新 schema；时刻实例复用 `YouthEventInstance`。
- simulation：`career/match-moment.ts`（判定 + 构造 + 位置意图注册表）。
- application：月度推进（青训与职业）接入生成检查；选项提交走既有 `submitCareerDecision`/`resolveCareerEvent`。
- web：`EventChoicePanel`/`EventFeedbackPanel` 以 `match` 场景条渲染（`storyId === 'match-moment'` 时），不新增页面；`match-moment/` 目录保留。
- content：不新增事件内容（意图为代码内注册表；作者化文案池留作后续）。

## 3. 测试与验收

- simulation：重要性判定（杯赛轮次/对手强度/出场门槛）；时刻构造（位置映射、三档 resolution 完整、引用比赛事实）；抑制度使 1,000 季重要比赛时刻数落在合理区间；同种子同操作完全一致。
- application：月度推进在重要比赛周打断并返回待决时刻；提交选择后状态效果与反馈落账；读档重入不重复生成；普通比赛周零打断。
- web：关键时刻以比赛场景渲染选项与反馈（聚焦测试）。
- 门禁全绿；1,000 季平衡：完成率 100%、每月最多 2 决策、重伤率 ≤1%、毕业率/承诺兑现率相对模块 6 基线（60.9% / 97.37%）偏移可解释；新增"关键时刻数"分布记录。
