# 完整青训赛季垂直切面设计

> 状态：已获用户批准，等待书面设计复核。
>
> 日期：2026-08-07
>
> 长期产品基准：`spec.md`
>
> 项目进度入口：`docs/ROADMAP.md`

## 1. 目标

玩家从 16 岁中国外场青训球员开始，完成一个从 9 月至次年 6 月的可信青训赛季。玩家通过训练选择、比赛表现、健康管理、队内竞争和人物事件影响发展，但不能直接控制结果。赛季结束时，系统基于真实账本生成评价和下一阶段状态。

本切面用于证明以下核心能力可以共同稳定运行：

- 月度玩家节奏与逐周内部模拟。
- 缓慢且有上限的属性成长。
- 固定青训球队、赛程、对手和位置竞争。
- 疲劳、伤病、恢复和比赛可用性。
- 教练、队友、竞争者及具体人物记忆。
- 有条件、有冷却、有因果的事件。
- 有限的一线队观察、跟训、名单和少量出场。
- 原子自动存档、刷新恢复及旧存档迁移。
- 赛季总结及 1,000 赛季批量平衡验收。

## 2. 范围

### 2.1 包含

- 创建球员和选择青训机构。
- 一个完整青训赛季。
- 持续生效的训练重点和强度。
- 逐周训练、比赛、恢复、疲劳和健康结算。
- 按月推进和月报。
- 固定青训球队、赛事和赛程。
- 持续存在的教练、关键队友和同位置竞争者。
- 日常记录、自动事件和决策事件。
- 动态发展信号及有限一线队通道。
- 低概率被当前机构放弃及补救路线。
- 赛季评价、下一阶段状态和完整账本。

### 2.2 不包含

- 完整一线队职业赛季。
- 正式职业合同谈判。
- 转会市场和海外联赛。
- 国家队。
- 成年重要比赛交互。
- 长期职业荣誉和退役。
- AI 生成叙事。

不得为不在本切面中的功能提前扩大共享契约、建立空壳用例或创建占位界面。

## 3. 玩家流程

```text
创建球员
→ 选择青训机构
→ 进入青训生涯首页
→ 设置训练重点与强度
→ 推进到下个月
→ 内部逐周模拟
→ 必要时暂停处理决策事件
→ 自动继续本月剩余周数
→ 查看月报
→ 重复至赛季结束
→ 查看赛季总结与下一阶段状态
```

玩家不逐周点击。单周推进只作为模拟层能力和开发调试入口保留。

## 4. 时间与月度推进

### 4.1 时间模型

- 玩家操作单位：月。
- 模拟结算单位：周。
- 赛季范围：9 月至次年 6 月。
- 每次推进按顺序处理本月剩余周数，不能直接跳日期。

### 4.2 月内内容

月内内容分为三类：

1. 日常记录：常规训练、普通比赛、恢复和轻微波动，只进入月报。
2. 自动事件：首次首发、连续稳定表现、伤愈、位置变化等，突出显示但不要求选择。
3. 决策事件：训练风险、伤痛处理、位置竞争、人物冲突、一线队机会和去留，暂停推进。

一个月可以没有决策事件，也可以按时间顺序出现多个。系统不得强制每月生成事件。多个事件必须具有合法因果或时间顺序。

### 4.3 推进事务

`advanceCareerMonth` 负责：

1. 校验没有未处理事件。
2. 锁定本月训练计划和随机状态。
3. 依次调用唯一的周模拟入口。
4. 每周追加账本并更新推进游标。
5. 遇到决策事件时保存事件和剩余周数，然后返回暂停状态。
6. 事件选择提交后继续同一个月，而不是开启新月份。
7. 全月完成后从账本生成月报。

批量模拟、网页推进和测试必须复用同一个周模拟及状态归并入口，不得复制实现。

## 5. 球员成长模型

### 5.1 长期基础

球员具有：

- 16 项可见属性的分项潜力或潜力区间。
- 早熟、常规或晚熟的成长节奏倾向。
- 稳定性、职业素养、抗压、适应力和伤病倾向。

这些信息只向玩家显示模糊评价，不显示精确值。

### 5.2 当前状态

每周更新、每月汇总：

- 体能。
- 累积疲劳。
- 士气。
- 比赛状态。
- 自信。
- 伤病和恢复进度。

体能表示当前可用程度，疲劳表示持续负荷；短期休息不能立即消除全部累积疲劳。

### 5.3 成长结算

- 训练和比赛产生内部发展积累。
- 可见属性每月统一结算。
- 普通球员单项赛季增长通常为 0–2。
- 表现突出且训练适配的属性可以增长约 3 点。
- 单周不显示频繁的属性 `+1`。
- 高潜力提高成长机会和上限，但不保证兑现。
- 身体、技术和精神属性使用不同年龄曲线。
- 高疲劳、错误训练、缺少比赛和伤病会降低成长效率。

### 5.4 动态发展信号

系统按月派生可逆信号：

- 快速发展。
- 一线队关注。
- 稳定成长。
- 发展停滞。
- 过度训练风险。
- 伤病受挫。
- 位置竞争压力。
- 被放弃风险。

信号决定候选机会和事件，不锁定最终路线。赛季总结中的“天才”“按部就班”“后来居上”或“天赋兑现隐忧”是对实际经历的归纳，不是开局时预设的剧本。

## 6. 训练与健康

### 6.1 训练计划

训练重点和强度持续生效，玩家需要时才调整。训练重点包括技术、位置专项、身体、战术和恢复；强度包括轻度、正常和高强度。

训练效果考虑分项潜力、年龄、职业素养、教练、设施、适配、比赛时间、健康和受控随机。高强度具有收益递减；疲劳过高时继续加量可能降低实际收益。

### 6.2 伤病风险

伤病风险由以下因素共同决定：

- 伤病倾向。
- 当前疲劳和体能。
- 训练强度和近期负荷。
- 比赛时间。
- 是否带伤训练。
- 既往伤病。
- 恢复和医疗条件。

轻度和正常训练的伤病风险不能恒为零，高强度风险也不能是对所有球员相同的固定百分比。

### 6.3 伤病阶段

- 轻微不适：可能不缺席，但影响状态和复发风险。
- 小伤：通常缺席 1–3 周。
- 中等伤病：通常缺席 4–8 周。
- 严重伤病：首赛季极少发生。

伤病经历初评、治疗选择、恢复、复训和逐步恢复比赛时间。单次小伤不永久降低所有属性；长期或反复伤病才可能影响部分身体属性和成长效率。

## 7. 青训机构、赛程与比赛

### 7.1 青训机构

机构内容属于 `packages/content`，至少包含：

- 地区、设施和教练质量。
- 竞争强度和培养风格。
- 青年赛事级别。
- 一线队实力层级和提拔倾向。
- 生活成本和异地适应压力。

强机构提供更好环境但竞争更激烈；中等机构资源一般但出场更多；校园和异地路线具有不同机会与代价。

### 7.2 固定赛季

- 赛程生成后立即固定并写入存档。
- 普通赛季约 18–26 场青训比赛。
- 包含准备期、联赛或区域赛事、友谊赛、冬季调整和赛季冲刺。
- 普通比赛进入月报，关键比赛和首次经历可以单独展示。

### 7.3 队内竞争

第一版生成 5–8 名持续存在的关键队友，其中至少一名同位置竞争者；其余阵容使用位置深度和球队整体实力表达。

队内地位按月评估：

```text
边缘球员 → 轮换 → 常规出场 → 青训主力 → 一线队观察
```

评估考虑相对能力、近期状态、健康、教练评价、战术适配、训练表现和培养目标。

### 7.4 比赛一致性

- 先生成完整球队结果，再分配玩家事件和数据。
- 玩家进球不能超过本队进球。
- 助攻必须对应本队进球。
- 未出场球员没有评分和比赛统计。
- 替补出场时间必须符合换人时间。
- 评分按位置职责计算。
- 球队实力来自阵容、战术、状态、疲劳和主客场，而不是只来自玩家属性。
- 强队通常更有优势，但允许合理爆冷。

## 8. 人物与关系

第一赛季维护：

- 一名青训主教练。
- 一名专项或助理教练。
- 2–4 名关键队友。
- 至少一名同位置竞争者。
- 必要时出现家人、球探和一线队教练。

人物具有稳定 ID、角色、性格、信任、尊重、亲近、具体记忆和当前态度。事件只影响实际参与人物，不能把同一记忆无差别添加给所有教练和队友。

教练关系信任与竞技评价分离：前者反映态度和执行可靠性，后者反映能力、状态和战术适配。玩家只看到模糊趋势。

## 9. 事件系统

事件资格至少考虑：

- 赛季阶段、年龄和位置。
- 训练、体能、疲劳、士气、状态和伤病。
- 队内地位、实际出场和近期比赛事实。
- 具体人物关系。
- 前置、互斥和真实周冷却。
- 机构与地区环境。
- 本月已有事件密度。

媒体关注必须由突出表现支持；一线队跟训必须先进入观察名单；伤病选择必须存在真实伤情；位置竞争必须关联同位置人物。事件内容必须通过 Schema、引用和效果白名单校验。

## 10. 有限一线队通道

一线队机会依次为：

```text
观察名单 → 跟训邀请 → 跟训评价 → 比赛名单 → 替补出场 → 极少数首发
```

每一级要求前置经历和当前资格。机会考虑年龄、当前能力、青训表现、位置需求、教练评价、稳定性、抗压和健康。过早提拔可能增加压力、疲劳和出场不足，不是纯奖励。

本切面只模拟与玩家直接相关的一线队名单和少量出场，不维护完整职业联赛，也不开始职业合同谈判。

## 11. 赛季结算

赛季总结从账本生成，至少覆盖：

- 出场身份和比赛数据。
- 属性成长和成长效率。
- 健康、缺席和恢复。
- 教练评价和关键关系。
- 一线队经历。
- 动态发展趋势。
- 留队、重点培养、观察、降级培养或被放弃结果。

首赛季被放弃属于低概率，并提供校园队、低级青训或其他机构试训。单次坏比赛或随机事件不能直接导致淘汰。

## 12. 数据与架构

依赖方向保持：

- `contracts`：稳定契约和存档边界。
- `content`：地区、机构、赛事、赛程模板、人物原型和事件。
- `simulation`：确定性的时间、成长、比赛、健康、关系和事件规则。
- `application`：月度推进、选择提交、存档和赛季结算。
- `web`：交互与显示，不定义模拟规则。
- `tools/balance`：批量模拟和报告。

内容加载必须校验重复 ID、引用、范围、赛程冲突、事件链和效果字段。simulation 中不得硬编码青训机构、对手和人物名称。

过大的界面组件应拆成球员概览、月度控制、训练计划、队内状态、关系、时间线和月报等单一职责组件。

## 13. 存档、错误与恢复

- 新存档使用 `schemaVersion: 2` 和明确内容版本。
- 提供 v1 到 v2 的迁移。
- 无法迁移时保留原始数据并显示诊断，不静默删除。
- 事件生成后先保存，再展示。
- 选择只能提交一次，保存后才继续推进。
- 月报从账本生成，不维护第二套冲突状态。

玩家可见错误区分存档不兼容、损坏、内容错误、待处理事件、推进失败和存储失败，并提供重试、返回事件、诊断或开始新生涯等恢复操作。

## 14. 测试与平衡

### 14.1 单元和集成测试

必须验证：

- 月度周数和跨年正确。
- 状态归并使用最终值。
- 事件冷却按真实周递减。
- 属性按月结算。
- 伤病风险受负荷和伤病倾向影响。
- 比分、出场和个人数据一致。
- 关系只影响参与人物。
- 一线队机会遵守阶梯。
- 淘汰不由单次随机决定。
- 同种子与同操作产生相同状态。
- 月度推进、逐周调试和批量模拟复用同一规则。

禁止永远为真的断言，禁止在未找到应出现样本时用空断言放行。

### 14.2 E2E

浏览器测试必须真实完成创建、青训选择、训练调整、月度推进、事件选择、月报、刷新恢复和赛季总结，不能只检查按钮存在。

### 14.3 批量模拟

`tools/balance` 运行 1,000 个青训赛季并输出 JSON 与可读报告。初始目标：

- 所有赛季完成，无非法存档或卡死。
- 每季约 18–26 场青训比赛。
- 通常每季 6–12 个决策事件，允许个别更少或更多。
- 普通球员单项成长通常为 0–2，超过 3 较少见。
- 一线队观察属于少数，正式出场属于极少数。
- 被当前机构放弃和严重伤病均为低概率。
- 强队胜率更高但存在合理爆冷。
- 不同种子的重大人物和事件组合具有差异。

范围参数集中在平衡配置中，根据报告调整，不散落在业务代码和测试夹具中。

## 15. 开发工作包

1. 稳定基线：修复当前契约、存档、状态归并、事件冷却、测试和格式问题。
2. 可信模拟核心：月度推进、成长、疲劳、伤病、固定赛程和一致比赛数据。
3. 青训环境与轨迹：机构、位置竞争、人物、动态信号和有限一线队通道。
4. 完整玩家流程：月报、事件中断、赛季总结、迁移和错误恢复。
5. 平衡验收：1,000 赛季模拟、参数校准及完整质量门禁。

每个工作包完成后项目必须可运行。不得先扩大共享契约，再连续提交多个不完整功能。

## 16. 明确决策

- 第一垂直切面终点：完整一个青训赛季。
- 一线队范围：有限跟训、名单和 0–3 次左右的稀少出场机会，不模拟完整职业赛季。
- 淘汰强度：首赛季低概率被当前机构放弃，并提供补救路线。
- 玩家节奏：按月推进，内部按周模拟。
- 训练控制：设置后持续生效，需要时调整。
- 轨迹模型：数值驱动加阶段门槛，不预设固定命运。
- 一个月可以有多个事件，也可以没有事件。
