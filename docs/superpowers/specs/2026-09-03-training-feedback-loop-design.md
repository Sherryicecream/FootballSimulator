# 训练反馈闭环设计

> 状态：待用户书面复核
>
> 日期：2026-09-03
>
> 长期产品基准：`spec.md`
>
> 当前进度入口：`docs/ROADMAP.md`

## 1. 背景与问题

当前训练计划可以持续生效，模拟层也已经计算训练负荷、疲劳、体能、伤病和发展积累，但玩家在界面上只能看到两个下拉框，以及月末“有几项属性提升”的摘要。训练选择与比赛出场、比赛评分和身体状态之间缺少一条可读的因果线。

当前还有两个体验问题：

- `CareerDashboard` 内有一套训练控制，`TrainingSettings.tsx` 另有一套未接入的训练组件，信息重复且表达不一致。
- `MonthlyReport` 只存在于页面临时状态，刷新或重新读档后会丢失最近一次月报，玩家无法回看刚刚做出的训练选择产生了什么结果。

本模块的目标是让玩家在每个月结束时回答三个问题：

1. 我本月实际训练了什么、承受了多少负荷？
2. 训练对成长、体能、疲劳和伤病产生了什么可观察影响？
3. 这些状态如何与本月的出场和比赛表现同时出现？

## 2. 目标与非目标

### 2.1 目标

- 保留一个持续生效的训练计划，玩家仍按月推进，不增加周度点击或快速跳过按钮。
- 由模拟层从已发生的训练、健康、成长和比赛事实生成结构化训练反馈。
- 青训和职业阶段都使用同一套反馈语义，分别接入现有月度推进用例。
- 月报展示计划、实际负荷、属性变化、体能/疲劳变化、伤病状态和比赛联系。
- 最近一次月报及训练反馈可随存档恢复，避免刷新后信息消失。
- 旧存档可以正常迁移；旧账本缺少结构化训练证据时，显示“暂无完整训练记录”，不猜测历史结果。
- 删除未接入的重复训练组件，训练控制只保留一处，减少冗余。

### 2.2 非目标

- 不重写现有成长公式、训练负荷公式、比赛引擎或伤病模型。
- 不把属性变化归因成训练的确定性结果；反馈应表达“本月训练与成长/比赛同时发生”，而不是声称单一因素决定结果。
- 不引入 AI 文本生成、动态图片或新的剧情事件。
- 不显示隐藏潜力、职业素养、伤病倾向等精确值。
- 不把内部周模拟暴露为玩家可操作流程。

## 3. 设计原则

### 3.1 数据流

```text
训练计划
  → simulation 周模拟：训练负荷、健康、发展积累、比赛事实
  → application 月末结算：月度成长、月报、持久化最近月报
  → web：只渲染保存的 TrainingFeedback 与 MonthlyReport
```

训练效果仍由现有唯一周模拟入口产生。反馈是对已经结算事实的解释层，不在 UI 中复制负荷、疲劳、伤病或成长规则。

### 3.2 真实性边界

- 训练负荷使用模拟实际产生的每周负荷总和，不用“训练强度 = 收益”的静态文案替代。
- 体能和疲劳展示月初到月末的真实变化；如果训练收益被比赛、恢复不足或伤病抵消，反馈应允许显示“没有可见属性提升”或“身体状态变差”。
- 比赛联系只使用本月真实比赛事实：出场次数、分钟数、评分和未出场情况。文案使用“本月表现受到……限制/与……同步”的谨慎表达，不证明不存在的因果。
- 伤病只显示本月实际发生、持续或恢复的状态，不按高强度固定生成伤病。
- 所有统计和分类由确定性函数生成，同一种子、存档和内容输入必须得到相同反馈。

## 4. 数据契约

### 4.1 结构化训练周事实

扩展训练账本事实，新增可选的结构化训练上下文，至少包含：

- `focus`：技术、位置专项、身体、战术或恢复。
- `intensity`：轻度、正常或高强度。
- `load`：该周实际训练负荷，包含训练与比赛负荷的既有计算结果中的训练部分。

字段放在现有账本条目的可选字段中，旧账本仍可通过原有摘要校验。青年和职业周模拟都写入同样结构，避免 application 解析中文摘要。

### 4.2 `TrainingFeedback`

在 contracts 中新增严格 schema，并作为 `MonthlyReport` 的可选字段，以兼容旧月报。反馈包含：

- 本月计划：`focus`、`intensity`、`positionFocus`。
- 执行情况：结构化训练周数、总负荷、平均周负荷。
- 成长结果：本月实际结算的属性变化，引用现有 `attributeChanges` 结构。
- 身体结果：月初/月末体能和疲劳的旧值、新值与变化量。
- 健康结果：`none`、`active`、`recovered` 三种状态，以及有数据时的伤情摘要。
- 比赛联系：出场次数、分钟数、平均评分（无评分时为 `null`）和受限原因分类；分类至少覆盖“表现正常/表现积极/疲劳限制/伤病限制/本月未出场”。
- 一条短的结构化结论和一条下一月建议，均由 application/simulation 生成，UI 不拼接规则性结论。

反馈不写入新的随机字段，也不改变 `careerPhase`、`monthlyAdvance` 或任何比赛结果。

### 4.3 最近月报持久化

在当前存档契约中增加可空的 `lastMonthlyReport`：

- 月度结算完成时写入完整月报，包含 `TrainingFeedback`。
- 事件暂停期间保留上一份已完成月报；不会把未完成月份伪装成已结算结果。
- 月度游标同时保存可选的 `feedbackStartHealth` 月初健康快照；推进中断或刷新恢复时沿用该快照，月报完成后清空。
- 开启新赛季时清空上一赛季的最近月报，避免新赛季首页展示旧月份。
- 旧 v1–v5 存档迁移为 `null`，不回填未经证实的训练影响。
- 页面加载时从存档恢复最近月报，内存中的 `report` 只作为当前交互状态的镜像。

该字段是可选兼容扩展，不升级随机序列，不改变旧存档的比赛与成长结果。若历史存档因缺少反馈字段而通过迁移，月报仍可继续显示原有事实和属性变化。

## 5. 界面方案

### 5.1 训练计划卡片

保留 `CareerDashboard` 现有控制作为唯一入口，并改成“计划 + 预期取舍”的视觉结构：

- 顶部显示当前训练重点和强度，并使用语义足球图标。
- 下方用三个短标签表达预期方向：成长重点、身体负荷、恢复压力。
- 这些标签只描述计划方向，不直接显示精确收益率或承诺结果。
- 计划修改后立即保存，月报仍以该月实际生效的计划为准。

`TrainingSettings.tsx` 不再保留为第二套独立组件；如果没有其他引用，删除该死代码及其专属测试/样式，相关断言迁移到仪表盘训练卡片。

### 5.2 月报中的训练反馈卡

在现有月报摘要之后增加“训练回顾”卡，按视觉顺序展示：

1. 训练计划：重点、强度、完成周数和负荷条。
2. 实际影响：属性变化，以及体能/疲劳的数字变化。
3. 健康提示：恢复良好、负荷偏高、伤病持续或本月恢复等明确状态。
4. 与比赛同屏：出场、分钟、平均评分和本月比赛联系结论。
5. 下一步：来自结构化反馈的短建议，例如保持、降低负荷或优先恢复。

卡片使用现有设计系统的颜色和语义图标：绿色代表正向结果，琥珀色代表取舍/注意，红色只用于真实伤病或明显风险。数字变化使用 `+/-` 和旧值→新值同时呈现，避免只给情绪化文案。

没有比赛、没有属性变化或旧存档缺少结构化证据时，卡片显示明确空状态，而不是重复“现场结果”或生成泛化剧情。

### 5.3 移动端与可视性

- 训练反馈在窄屏下单列堆叠，负荷条不依赖颜色，旁边同时显示文字和数值。
- 所有图标带 `aria-label` 或隐藏文本，颜色不是唯一信息来源。
- 现有比赛日回放、月度动量和故事进度保留，不让训练卡遮盖本月主线；训练反馈作为“发生了什么”的事实层，比赛回放作为“比赛里发生了什么”的场景层。

## 6. 兼容与错误处理

- 所有新 schema 使用严格对象；新字段只在新增/更新数据中写入，迁移旧数据时提供明确默认值。
- `TrainingFeedback` 生成遇到旧账本缺少训练上下文时返回可验证的缺省状态，不读取摘要文本猜测负荷。
- 月报生成失败不得吞掉月度结算；application 应保留已结算存档，并返回没有训练反馈的兼容月报，同时记录可诊断错误。
- UI 对缺失 `trainingFeedback` 使用原有月报展示，不崩溃、不出现空白训练区块。
- 更新训练计划仍遵守待处理事件阻塞规则，并由 application 用例执行 schema 校验。

## 7. 测试与验收

### 7.1 先写的回归测试

- contracts：新训练上下文、`TrainingFeedback`、`MonthlyReport` 和存档迁移的严格校验。
- simulation：同一输入生成相同训练反馈；训练负荷、健康变化、比赛统计取自真实事实；旧账本缺字段时返回可解释缺省状态。
- application：青年与职业月度推进均写入训练反馈和 `lastMonthlyReport`；事件暂停/恢复不会重复训练周或重复月报；下一赛季清空最近月报。
- web：训练计划只有一个可操作入口；月报展示训练、身体、成长和比赛联系；旧月报/无反馈时展示兼容空状态；刷新恢复最近月报。
- E2E：按月推进到月报，确认训练反馈可读；刷新后月报仍在；修改计划后下个月反馈反映新的实际计划。

### 7.2 完成门禁

除模块专项测试外，按项目要求运行：

- `pnpm test`
- `pnpm typecheck`
- `pnpm lint`
- `pnpm format:check`
- `pnpm build`
- `pnpm test:e2e`
- 路线图规定的 `1,000` 生涯平衡命令

平衡命令的完成率、比赛数、伤病率、毕业率、职业承诺兑现率等核心指标应与本模块前基线保持在可解释范围内；本模块若只改变展示与报告持久化，不应改变比赛结果、随机序列或成长分布。

## 8. 验收标准

- 玩家能在训练卡上看懂当前计划的取舍，但不会误以为训练承诺固定属性收益。
- 每次月报都能明确区分“训练做了什么”“身体发生什么”“比赛表现如何”。
- 有训练效果时显示实际属性和状态变化；没有效果时说明原因或显示真实的无变化状态。
- 青训和职业期展示口径一致，且不新增周操作。
- 刷新/重新读档后最近月报仍可查看；旧存档可继续运行。
- 全部质量门禁通过，且平衡基线没有因报告模块发生不可解释偏移。
