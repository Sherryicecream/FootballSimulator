# 职业期赛事深度设计

## 目标

在现有 v4 职业赛季月度流程上，加入一项可游玩的国内杯赛、球队表现对球员赛季体验的可解释影响、基于联赛排名的升降级，以及可供赛季总结和全生涯回放使用的荣誉记录。第一阶段只扩展职业期，不改青训月度推进、转会/租借市场和训练可视化规则。

## 当前上下文

- `ProSeasonState` 已固定职业俱乐部、完整联赛赛程、积分榜、阵容和深度图；`proSeason.fixtures` 必须继续保存完整联赛赛程。
- `simulateProfessionalWeek` 当前只模拟联赛赛程；球员出场影响个人统计和状态，但不影响本队比分。
- `completeProfessionalSeason` 当前只写入承诺复核和基础 `SeasonHistorySummary`，没有杯赛、排名变化或荣誉字段。
- 俱乐部内容是虚构的 3–8 级国内层级，每级 12 家；数字越大代表层级越高。职业期的球队世界只在球员存档中按需生成，没有独立的全联赛世界存档。
- `ProDashboard` 目前只展示联赛积分榜和联赛个人数据；`ProOffseasonPanel` 目前只展示联赛出场、个人数据和承诺复核。

## 非目标

- 第一阶段不实现多项杯赛、洲际赛事、真实俱乐部数据库或完整全国联赛世界模拟。
- 不把杯赛结果做成赛季末随机文本；每一场可影响球员的杯赛必须有固定赛程、确定性结果和可追溯账本事实。
- 不把 UI 作为第二套比赛规则；UI 只读取 application 返回的赛事与荣誉数据。
- 不改变每月最多 2 个互动事件、月度保存/恢复、职业阶段机和现有比赛随机序列边界。

## 方案选择

### 方案 A：在联赛结算上叠加杯赛标签

只在赛季末按照排名随机生成“杯赛经历”和荣誉。实现成本最低，但没有杯赛赛程、淘汰过程或球员对结果的影响，无法提供持续的游戏性。

### 方案 B：固定赛事集合，复用比赛引擎（采用）

保留 `proSeason.fixtures` 作为完整联赛赛程，新增职业赛季杯赛状态，使用同一 `ProFixture` 和 `simulateMatch` 生成 8 队、三轮淘汰赛。杯赛赛程在赛季创建时固定，比赛在对应职业周结算，结果、晋级和荣誉写入存档。联赛仍按现有积分榜结算，球员当前表现通过有限的球队强度修正影响本队赛果。

优点是可见、可重放、与现有月度流程一致，且不需要虚构完整的全国足球世界。代价是需要增加杯赛状态和一份球员职业期统计切片。

### 方案 C：完整全国联赛与多级杯赛世界

同时模拟所有层级、完整升降级和多项赛事。真实性上限最高，但会扩大存档、赛程、性能、UI 和平衡边界，超过当前模块的独立交付范围。

## 领域模型

### 职业赛季杯赛

在 `ProSeasonState` 中增加可选的 `domesticCup`，用于兼容旧 v4 存档：

```ts
type ProCupState = {
  id: string;
  name: string;
  competitionId: string;
  entrants: string[]; // 8 个固定俱乐部，包含球员所在俱乐部
  fixtures: ProFixture[]; // 只保存杯赛固定赛程，不与 proSeason.fixtures 混用
  currentRound: 'quarterfinal' | 'semifinal' | 'final' | 'complete';
  winnerClubId: string | null;
  completed: boolean;
};
```

杯赛三轮分别使用职业赛季后半段的空闲周（第 27、33、39 周），避免与现有 22 轮联赛赛程重复占用球员周比赛槽。每轮晋级队伍由上一轮比赛结果决定，未轮到的队伍不生成假结果。点球只在淘汰赛平局时使用确定性加时/点球判定，不改变联赛积分。

这项国内杯固定为 8 队单败淘汰、3 轮、全赛事共 7 场；单个俱乐部最多参加 3 场。界面中的 7/7 表示整项杯赛的赛事总进度，球员出场与个人数据另按当前俱乐部实际对阵统计。

杯赛参赛队从球员当前有效层级及相邻层级的国内俱乐部中用赛季种子稳定选择；球员所在俱乐部强制入选。若该俱乐部因上季升降级不再位于内容静态层级，赛季生成器用 `ProSeasonState` 的有效层级覆盖其内容层级，并从目标层级候选中补足 11 个对手。

### 球员影响球队结果

比赛顺序固定为：

1. 根据训练、健康、深度图和合同承诺决定球员是否首发/替补/预备队。
2. 根据球员加权能力、状态、出场分钟和对手强度计算有限的 `playerImpact`。
3. 将 `playerImpact` 只加入球员所在俱乐部的进攻/中场/防守强度，最大幅度为 ±4；未出场、重伤或预备队出场不影响一线队比分。
4. 调用现有确定性 `simulateMatch` 生成比分。
5. 生成球员表现、球队事实和比赛结果；杯赛另外更新晋级状态，联赛另外更新积分榜。

球员影响只作为球队强度的窄幅修正，不能让低级别球员单独碾压强队；球队基础强度、主客场和现有比赛波动仍占主要比例。球队表现反过来通过本场胜负、排名、杯赛晋级、士气/状态和赛季荣誉反馈给球员，使球员数据对生涯确实有可见后果。

#### 比分离散度与个人贡献归因

“simulateMatch”先按射正次数和攻防差计算预期进球数，再用固定一次离散波动抽样比分。转化率参数为 BASELINE = 0.20、RANGE = 0.34，并保留原有 20% 的 -1/0/+1 对称离散波动。扩大转化率区间让比赛在高转化日出现 5 球以上尾部、在低转化日保留 0–2 球小比分，同时不把平均进球数整体推高；比分仍受 MAX_GOALS = 10 限制，且随机源消费维持原有每场 2–3 次节奏并保持可复现。

个人数据由 allocatePlayerContribution({ ownGoals, minutes, position, shooting, passing, rng }) 从真实己方进球逐球归因。每球互斥地选择进球者、助攻者或未归因，未出场传入 0 分钟；位置基础权重（进球/助攻）如下，随后分别乘出场比例与对应能力因子：

| 位置   | 进球基础权重 | 助攻基础权重 |
| ------ | -----------: | -----------: |
| 中后卫 |         0.08 |         0.18 |
| 边后卫 |         0.10 |         0.28 |
| 后腰   |         0.14 |         0.38 |
| 中场   |         0.20 |         0.50 |
| 边锋   |         2.50 |         1.80 |
| 前锋   |         2.50 |         1.80 |

职业联赛、国内杯和青训固定赛均使用同一归因规则；预备队、未出场和无己方进球时个人进球/助攻均为 0。比赛评分可以小幅反映已归因贡献，但不再次把球队比分作为个人数据放大。

### 统计与账本

`ProSeasonStats` 增加杯赛出场、杯赛进球、杯赛助攻和杯赛分钟；现有联赛字段语义不变。所有职业统计按 `clubId` 和 `competitionId` 过滤，避免 `proSeason.fixtures` 或新增杯赛 fixtures 被重复计入。

新增的职业事实类型包括杯赛比赛、晋级/淘汰、联赛排名结算和荣誉获得。每条事实只引用实际参与的俱乐部或球员，不给未参与人物添加效果。

### 训练负荷与表现

职业周的基础训练负荷固定为轻量 24、正常 40、高强度 54；周总负荷按 `(基础训练负荷 + 5) × 1.05 + 本队赛事数 × 10` 计算，轻量计划的比赛项按 0.5 倍计，以体现恢复安排。训练反馈同时保留基础训练负荷与周总负荷。近期负荷以 64 左右为平衡区间：合理负荷小幅提升训练表现，长期过低或超过高负荷边界会降低准备度，并通过疲劳、体能与伤病模型产生可解释后果。所有计算仍由 simulation 使用显式存档输入和种子完成。

### 升降级

赛季结算只对球员所在联赛负责：

- 联赛排名第 1 名获得联赛冠军荣誉。
- 若当前层级低于最高层级，排名前 2 名获得升级；球员所在俱乐部若在前 2 名，下一赛季有效层级 `+1`。
- 若当前层级高于最低层级，排名后 2 名降级；球员所在俱乐部若在后 2 名，下一赛季有效层级 `-1`。
- 边界层级不生成越界移动；其余球队只生成可解释的“本队排名/层级变化”事实，不伪造未模拟联赛的完整积分榜。

`nextClubTier` 作为职业赛季结算结果保存并由下一季创建读取；旧存档缺失时回退到合同中的 `clubTier`。这使玩家能看到升降级并在下一赛季进入新层级，同时不引入第二份全国世界状态。

### 荣誉

新增 `SeasonHonour` 结构，至少包含 `id`、`kind`（联赛冠军/杯赛冠军/升级/个人赛季最佳）、`label`、`seasonId`、`clubId` 和 `evidenceId`。赛季历史保存本赛季荣誉数组，职业休赛期展示；职业回放和生涯总结只从赛季历史/账本读取，不重新计算。

第一阶段只授予有明确证据的球队荣誉：联赛冠军、杯赛冠军和升级。个人奖项暂不自动生成，避免没有奖项评选模型时制造不透明结果。

团队荣誉权重保持联赛冠军 25、国内杯冠军 18；传奇维度进一步区分联赛冠军 12、国内杯冠军 8，国内杯是重要荣誉但低于联赛冠军，洲际/世界大赛冠军按更高档位计入。

## 数据流与兼容性

```text
startProfessionalSeason
  ├─ 固定联赛 fixtures + standings
  └─ 固定 domesticCup bracket + cup fixtures
        ↓
advanceProMonth → simulateProfessionalWeek
  ├─ 联赛：球员影响 → 比赛 → standings
  └─ 杯赛：球员影响 → 比赛 → 晋级/淘汰
        ↓
completeProfessionalSeason
  ├─ 排名、升降级和荣誉
  ├─ SeasonHistorySummary + ledger
  └─ nextClubTier → 下一赛季创建
```

所有新增字段都使用 v4 兼容默认值：旧存档没有 `domesticCup`、杯赛统计、荣誉或 `nextClubTier` 时，按“无杯赛、无杯赛统计、无荣誉、合同层级”加载。新赛季才创建杯赛，不给正在进行的旧赛季补造历史比赛。

## 前端表现

- 职业仪表盘增加“本赛季赛事”卡：分别显示联赛排名、杯赛轮次、最近杯赛结果和球队层级变化。
- 赛季数据同时显示联赛/杯赛出场与分钟；保留现有个人统计位置和无障碍文本。
- 职业休赛期总结显示“球队赛季”和“本赛季荣誉”两个区域，荣誉带有赛事图标和证据说明。
- 所有结果使用现有 `SceneBanner`、`FootballGlyph`、`StatusBadge` 视觉系统，不新增 UI 计算逻辑；移动端保持无横向溢出。

## 失败处理与确定性

- 固定赛程引用未知俱乐部、杯赛 bracket 不完整、晋级队伍不存在或重复结算时立即抛出领域错误，不静默生成结果。
- 相同保存、俱乐部内容、赛季种子和月度推进顺序必须得到相同杯赛签位、比分、排名、荣誉和账本。
- 杯赛使用独立的派生随机种子，不推进现有职业比赛随机游标；播放器选择判定、杯赛抽签和比赛结果的随机来源互不污染。
- 保存/刷新发生在杯赛前、杯赛后和赛季结算后，都必须保留 bracket、已赛 fixture、晋级状态、统计和荣誉。

## 验证计划

### 契约与迁移

- 新杯赛结构完整性、三轮数量、重复俱乐部和旧 v4 缺失字段的默认值。
- 新增统计和 `SeasonHistorySummary.honours` 的合法范围；旧 season history 继续通过 schema。

### simulation/application

- 同输入杯赛签位和比赛结果完全一致，且不改变旧联赛随机序列。
- 高能力且稳定出场的球员对球队强度影响为窄幅正向；伤病/未出场不产生本队修正；低能力不保证必败。
- 联赛排名正确生成冠军、升级、降级和边界层级保护；杯赛晋级只由杯赛结果推动。
- 月度推进在杯赛周生成对应事实；赛季结算只生成一次荣誉和一次 `nextClubTier`。
- 旧 v4 存档能继续推进；中途保存/加载前后杯赛和联赛状态一致。

### web/E2E/balance

- 仪表盘和休赛期显示联赛/杯赛/荣誉；旧反馈与旧赛季页面保持兼容。
- 桌面和移动端完成至少一场杯赛、一次晋级/淘汰和一次赛季总结。
- 运行项目规定的全量测试、类型、Lint、格式、构建、E2E 和 1,000 季平衡报告；特别记录 balance runner 的耗时，不用低样本替代完整命令。

## 验收标准

1. 新职业赛季会固定生成包含球员俱乐部的 8 队国内杯赛，杯赛结果可在月度流程和存档中看到。
2. 球员当前能力、状态、健康和出场情况会对球队比赛结果产生窄幅、可解释、可复现的影响。
3. 联赛冠军、杯赛冠军和边界内的升级/降级会进入赛季历史、账本和职业休赛期总结。
4. 旧 v4 存档、现有联赛统计、承诺复核、月度恢复和既有 E2E 流程保持兼容。
5. UI 只展示 application 结果，不复制任何比赛、杯赛或升降级规则。
