# 选择结果判定引擎设计

## 背景

当前剧情选择主要应用固定效果，多个选项缺少与球员能力、当前状态和比赛情境相关的结果差异。玩家因此很难感受到“我是谁”会影响“我怎么处理事情”，也无法从结果中理解自己的选择为什么成功或失败。

本模块把一次选择从“直接应用固定数值”扩展为“先判定，再应用对应结果”，同时保持旧事件可继续运行，并保证存档加载和回放具有确定性。

## 目标

1. 同一事件的不同选项可以配置不同的判定属性、难度和结果反馈。
2. 判定结果至少分为成功、部分成功、失败三档；结果可以有不同的数值效果和剧情反馈。
3. 判定使用球员当前能力、当前状态和明确的种子随机波动，不使用不可复现的运行时随机数。
4. 结果、判定依据和实际影响写入账本，刷新页面或重新加载存档后不改变。
5. 前端能让玩家看出结果与自身能力/状态有关，但不复制模拟规则。
6. 没有新判定配置的旧事件继续按照原有静态效果运行。

## 非目标

- 本模块不重做训练系统。
- 本模块不引入职业联赛、杯赛、升降级或转会市场规则。
- 本模块不要求每个旧事件立即改写；先提供兼容能力，再逐步丰富内容。
- 本模块不把结果判定放入 Web 组件。

## 方案

每个需要判定的选择增加可选的 `resolution` 配置：

- `attribute`：本次选择关注的主能力。
- `difficulty`：内容定义的基础难度。
- `volatility`：可选的确定性波动范围，用于避免结果完全由单一阈值决定。
- `stateModifiers`：允许内容声明哪些当前状态参与修正及其权重。
- `outcomes`：成功、部分成功、失败三套结果定义。

结果定义沿用现有选择效果的表达方式，并额外支持结果标签、回应文本、后续提示、记忆键和后续事件。这样可以让一次“澄清误会”在不同结果下产生不同的教练回应、信任变化和后续剧情，而不是统一显示“事件暂时告一段落”。

概念示例：

```ts
resolution: {
  attribute: "decisionMaking",
  difficulty: 62,
  volatility: 8,
  stateModifiers: {
    confidence: 0.15,
    fatigue: -0.1,
  },
  outcomes: {
    success: { label: "沟通奏效", effects: { coachTrust: 3 } },
    partial: { label: "误会暂时缓和", effects: { coachTrust: 1 } },
    failure: { label: "解释被认为是在推诿", effects: { coachTrust: -3 } },
  },
}
```

示例只说明结构，实际能力键和可用状态键以现有 contracts 为准。

## 判定流程

模拟层提供纯函数，输入显式包含球员快照、选择配置、事件上下文和种子：

1. 读取选择指定的主能力。
2. 根据配置读取当前士气、信心、疲劳、教练信任等状态修正。
3. 使用 `careerId + eventId + choiceId + resolutionSeed` 生成稳定波动。
4. 得到本次判定分数，并按内容定义的难度和结果区间选择三档结果。
5. 返回结果类型、分数摘要、解释标签和结果效果；不直接修改 career save。

推荐的解释数据包括：主能力名称和当前值、状态修正方向、结果类型以及实际应用的效果。具体数值是否完整展示由 UI 决定，但不得由 UI 重新计算。

对于缺少 `resolution` 的旧选择，模拟层返回兼容结果，应用原有 `effects` 和 `delayEffects`，并标记为 `legacy`，避免历史存档行为改变。

## 分层职责

### contracts/content

- 校验 `resolution` 和三档 outcome 的结构。
- 复用现有效果字段，限制数值类型和合法能力/状态键。
- 保持所有配置可序列化，以便内容测试和存档迁移。

### simulation

- 实现确定性的纯判定函数。
- 不读取全局随机源，不访问浏览器或外部服务。
- 只根据传入的内容、球员快照和种子计算结果。

### application

- 在现有事件解决用例中调用判定函数。
- 只应用判定返回的 outcome effects。
- 将 outcome、判定摘要、选择和实际变化写入 career ledger/facts。
- 生成结果反馈并清除 pending event。

### web

- 显示结果徽章、回应正文、后续影响和简短的“为什么”说明。
- 不实现阈值、随机或效果计算。
- 对旧事件继续显示兼容反馈。

## 可解释性与真实性约束

- 能力值高不等于必定成功；状态和有限波动可以造成边界结果。
- 波动范围必须受内容配置限制，不能压过主能力的长期作用。
- 失败不应总是惩罚，应允许内容定义关系、状态和后续事件的不同代价。
- 判定原因必须可以从保存的输入和账本记录中复盘。
- 结果只影响事件明确参与的球员、关系和职业状态，不扩散到无关人物。

## 测试与验收

在实现行为前先增加失败回归测试，至少覆盖：

1. 同一输入和种子得到完全相同的结果。
2. 高能力/有利状态在相同条件下整体优于低能力/不利状态。
3. 三档结果分别应用各自效果和反馈。
4. 边界波动不会越过配置允许的范围。
5. 旧选择没有 `resolution` 时仍应用原静态效果。
6. 应用用例会保存 outcome 和解释信息，并正确清理 pending event。
7. 旧存档可以通过 schema 默认值加载。
8. Web 结果展示使用应用层返回的数据，不在组件内重算。

完成后运行项目要求的测试、类型检查、lint、格式检查、构建和端到端测试；本模块的阶段性检查点单独提交到当前分支。

## 自检结论

- 依赖方向符合项目约束：规则在 simulation，编排在 application，展示在 web。
- 旧事件和旧存档有兼容路径。
- 确定性来源明确，可以支持回放和刷新后复现。
- 该设计不会提前引入杯赛、荣誉或转会逻辑，但为后续赛季总结保留可追踪账本。
- 仍需在实现前确认具体能力键、状态键及现有效果字段名称，并以代码中的 contracts 为准。
