> 状态：待用户书面复核
>
> 日期：2026-09-04
>
> 长期产品基准：`spec.md`
>
> 当前进度入口：`docs/ROADMAP.md`

## 1. 背景

当前事件系统已经具备选择、能力判定、状态变化、关系变化、人物回应和后续事件等基础能力，但只有少量事件配置了完整的成功/部分成功/失败结果。大量旧事件仍会落入通用反馈路径，界面固定显示“现场结果”，玩家难以判断一次选择究竟带来了什么具体变化。

本模块的目标是把一次选择呈现为一段可读、可回放的足球生涯反馈：玩家能看到结果性质、主要回应、相关人物态度和后续影响，同时保持当前模拟的真实性、确定性与可解释性。

## 2. 目标与非目标

### 2.1 目标

- 使用已有的能力、士气、状态、疲劳、体能、教练评价和确定性临场波动决定结果，不新增另一套判定规则。
- 为纳入本模块的事件补齐成功、部分成功和失败三档结果文案。
- 每档结果拥有具体标题、主叙述、相关人物回应和后续影响。
- 反馈页不再对新结果统一显示“现场结果”，而显示具体结果标题，例如“误会暂时解除”“教练仍在观察”“误会加深”。
- 反馈内容写入现有 `EventFeedback`，可以保存、读档和重复展示。
- 旧事件和旧存档继续兼容；缺少结构化结果的历史反馈不重新猜测其影响。
- 不扩展为完整剧情图鉴，只覆盖高频事件和现有故事链的关键节点。

### 2.2 非目标

- 不重写选择判定、属性效果、关系效果、比赛结果、健康模型或阶段机。
- 不新增周度玩家操作，不改变月度流程、随机序列或事件冷却。
- 不让 UI 计算能力门槛、结果等级、关系变化或后续事件条件。
- 本模块不接入真实 AI provider。AI 仍只能作为未来的可选文本润色层，不能参与判定或生成新的数值事实。
- 不一次性把所有事件改写为完整多分支剧本。

## 3. 玩家体验

每次选择后的反馈按以下顺序展示：

1. **结果标题**：概括这次选择的实际结果，而不是固定写“现场结果”。
2. **结果类型**：成功、部分成功、失败或旧事件兼容结果。
3. **主叙述**：解释事件在训练场、比赛日、更衣室或场外如何暂时落地。
4. **人物回应**：教练、助教、队友、竞争者或家人的具体回应。
5. **变化记录**：已有的状态与关系变化，仍显示旧值、新值或增减量。
6. **后续影响**：说明下次训练、比赛或满足条件后的观察点。

对新事件，结果标题和主叙述由模拟/应用层生成并保存，UI 只负责展示。没有量化变化时，反馈应写明“影响尚未显现”或类似事实，不伪造属性变化。

## 4. 数据流与架构

```text
玩家选择
  → resolveChoiceOutcome：读取当前能力/状态并完成确定性判定
  → buildEventFeedback：选择结果文案、人物回应和后续影响
  → EventFeedbackSchema：严格校验并写入 pendingFeedback/账本
  → web：渲染已保存的结果标题与反馈内容
```

### 4.1 simulation/application 边界

- `resolveChoiceOutcome` 继续是唯一的选择结果判定入口。
- `buildEventFeedback` 继续是唯一的事件反馈组装入口，负责把结果等级映射到人类可读的反馈。
- 应用层负责保存、暂停、恢复和读档，不在 use case 中复制判定规则。
- web 不读取隐藏能力、不重算分数、不推断后续条件，只消费 `EventFeedback`。

### 4.2 结果标题来源优先级

对新事件，标题按以下顺序选择：

1. 确定性对话变体中作者定义的结果标题（若该变体提供）。
2. 结果分支中作者定义的 `label`，保持现有 `ChoiceResolutionOutcome` 兼容。
3. 选择级作者标题（用于没有能力判定的旧事件补充具体文案）。
4. 由已有结果等级和可用事件信息生成的固定兜底标题。

标题兜底只能改变表达，不能新增状态、关系或属性效果。相同存档、事件和选择必须得到相同标题与回应。

## 5. 契约设计

### 5.1 `EventFeedback`

在现有严格对象中增加兼容字段：

- `resultTitle?: string`：长度受限的具体结果标题。
- `resultTone?: 'success' | 'partial' | 'failure' | 'neutral'`：用于语义色彩和无障碍文本，不作为业务判定输入。

字段保持可选，以便旧 `pendingFeedback`、旧月报和历史存档继续通过 schema。新生成的结构化事件反馈应始终写入这两个字段。

### 5.2 内容输入

- 继续复用 `ChoiceResolutionOutcome.label` 作为结果标题的首选来源。
- `EventChoiceNarrativeVariant` 可选增加 `resultTitle`，仅影响文案选择，不影响数值结算。
- `EventChoice` 可选增加选择级 `resultTitle`，为不具备能力判定的旧事件提供作者化标题。
- 现有 `response`、`responses`、`followUp`、`nextEventIds` 和关系/状态效果字段保持兼容。

所有新增字段使用严格、有限长度的 schema。内容校验应拒绝目标事件缺失必要结果文案、参与人物角色不匹配或分支指向不存在事件的情况。

## 6. 内容范围

首批不覆盖完整内容包，而是覆盖以下 10 个高频/高价值事件：

- `misunderstanding-clarification`
- `misunderstanding-repair`
- `costly-match-mistake`
- `technical-plateau`
- `recovery-session-warning`
- `return-to-full-training`
- `position-race-opening`
- `position-race-review`
- `coach-trust-opening`
- `coach-trust-test`

覆盖规则：

- 每个选择拥有成功、部分成功和失败的独立反馈。
- 训练、比赛、关系和健康主题至少各有一个可见差异样本。
- 结果文案与事件场景匹配：训练事件体现教练观察和训练要求，比赛事件体现表现复盘，关系事件体现信任/尊重变化，健康事件体现恢复风险。
- 现有故事链的后续条件继续由原有 `nextEventIds`、故事记忆和事实条件控制，不因文案模块新增隐藏状态。
- 未纳入本批的事件保持原有效果；可补充选择级标题，但不强行伪造三档数值结果。

## 7. 错误处理与兼容

- 旧存档缺少 `resultTitle`/`resultTone` 时，读取流程使用明确的兼容标题，不回溯猜测过去的判定。
- 内容包在加载时验证结果文案、人物角色和后续事件引用；校验失败应阻止不完整内容进入模拟。
- 反馈生成遇到旧事件缺少结构化分支时，保留已有 `response`、人物默认回应和 `followUp`，同时使用 neutral 兼容结果标题。
- AI 或未来文本 provider 即使失败、超时或输出不安全，也只能回退到已验证的作者文案，不能改变结果、效果、参与人物或后续事件。
- UI 对字段缺失保持稳定，不出现空白结果卡，不因历史反馈缺字段而崩溃。

## 8. 测试与验收

### 8.1 契约与内容

- 新字段可以通过严格 schema，未知字段仍被拒绝。
- 旧 `EventFeedback`、旧 pending feedback 和历史 save 缺少新字段时仍可解析。
- 目标事件的每个选择都具备三档结果标题、主叙述和后续影响。
- 参与人物回应只能引用事件声明的参与角色。

### 8.2 simulation/application

- 相同 save、event、choice 的结果和文案深度相等。
- 调整当前能力、疲劳、士气或教练评价能够在可控范围内产生不同结果，但不改变随机序列推进方式。
- 成功、部分成功、失败分别返回不同的标题、主叙述或人物回应。
- 反馈中的状态/关系变化与最终 save 一致，不由文案反推数值。
- 事件暂停、恢复、保存和读档不重复应用效果，也不丢失结果标题。

### 8.3 web/E2E

- 新结果显示具体标题，不显示固定的“现场结果”作为主结果标题。
- 成功、部分成功或失败至少两条路径在标题和回应上可见不同。
- 旧反馈仍能正常显示兼容内容。
- 桌面和移动端刷新后，结果标题、人物回应和后续影响保持一致。

### 8.4 平衡门禁

继续运行项目要求的完整门禁：

- `pnpm test`
- `pnpm typecheck`
- `pnpm lint`
- `pnpm format:check`
- `pnpm build`
- `pnpm test:e2e`
- 路线图规定的 1,000 生涯平衡命令

验收时重点比较完成率、比赛数、决策密度、伤病率、毕业率、职业承诺兑现率和故事主题覆盖率。文案层不应造成不可解释的核心分布变化。

## 9. 发布边界

本模块完成后，玩家可以在关键事件中看到“选择 → 结果 → 人物回应 → 后续影响”的完整反馈链，但仍不会看到完整剧情百科，也不会要求每周操作。下一阶段再根据本地体验决定是否扩展更多内容，或单独设计真实 AI provider 的接入方案。
