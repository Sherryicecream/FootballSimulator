# 故事图谱与内容扩展设计

日期：2026-09-01
状态：已获批准，作为第一个后续模块的实现边界

## 目标

把“做出选择后只显示一条现场结果”扩展为可持续推进的短故事链：玩家每次只看到当前场景，做出选择后立即得到针对性反馈，并留下下一次事件会读取的故事状态。内容要有足球职业语境、角色回应和后续悬念，但不能变成一次性铺满的剧情图鉴。

## 非目标

- 本模块不引入比赛逐分钟模拟、周推进或新的职业阶段。
- 本模块不接入外部大模型或网络服务。
- 本模块不重做完整视觉系统；只提供事件需要的场景元数据，供现有 UI 渲染。
- 本模块不让事件效果修改未参与事件的人物，也不新增无法从存档恢复的隐式状态。

## 用户体验

一个故事链由 2–4 个短场景组成。当前场景包含：

1. 事件标题、地点、涉及人物和简短上下文；
2. 2–3 个有明确语气差异的选择；
3. 选择后的即时回应：主角行动结果、教练/队友/经纪人等参与者的回应，以及下一步线索；
4. 一个可在后续月份触发的故事游标或事实，而不是展示完整剧情目录。

例如“澄清误会”不会只得到“现场结果”，而会得到教练态度变化、队友的短句回应，以及“下一场训练前找队长谈谈”之类的后续方向。不同选择应产生不同反馈，但都必须能落到明确的事实、关系、状态或后续事件条件上。

## 数据与边界

### 故事定义

在 contracts 中增加可序列化的故事链定义：

- `storyId`：稳定 ID；
- `nodes`：带 `nodeId`、事件内容引用和可选进入条件的短场景；
- `edges`：从当前节点到下一个节点的选择映射、延迟月份和条件；
- `facts`：进入、完成和失败时写入的职业事实名；
- `participants`：节点明确涉及的人物 ID。

节点继续复用已有事件选择、叙事变体和显式 effects，不平行创造第二套效果系统。故事边只负责“何时、因何进入下一个节点”，不直接绕过 application 改阶段或改存档。

### 确定性

- simulation 只接收已解析的内容和 seed；
- 同一个 seed、故事状态和选择序列必须得到同样的节点、反馈和下一个事件；
- 变体选择继续使用稳定哈希，不能依赖随机游标顺序；
- 故事游标、延迟月份和已写入事实必须进入 save/reload 路径。

### 应用层职责

application 负责：

- 依据月结算结果推进故事游标；
- 把故事节点转成现有 pending event；
- 在选择后持久化反馈和下一个节点线索；
- 兼容没有故事字段的旧存档。

### Web 层职责

web 只呈现当前节点和反馈，不复制进入条件、效果或推进规则。当前模块只做小范围信息层增强：显示“故事进度/下一步线索/参与者回应”，不做完整图鉴页。

## 首批内容

优先提供三条互相独立、可复用现有人物的短链：

1. `misunderstanding-clarification`：误会澄清 → 教练信任 → 训练安排变化；
2. `selection-bubble`：入选边缘 → 是否主动竞争 → 进入名单或继续观察；
3. `recovery-return`：伤后复训 → 控制负荷或提前证明 → 回归评价。

每条链至少 2 个节点，每个关键选择至少 2 个完整叙事变体。没有满足条件时，事件不能强行出现；链条结束后应写入完成事实并允许同类内容在未来以新实例再次出现。

## 实施与验证顺序

1. 先为 contracts、content、simulation、application 写失败测试，覆盖 schema、条件、确定性、存档恢复和参与者边界。
2. 实现最小故事图谱模型与确定性节点解析。
3. 接入月结算和 pending event，保留旧事件兼容路径。
4. 增加三条首批内容并运行内容校验。
5. 更新当前事件 UI，使反馈、参与者回应和后续线索可见。
6. 运行完整测试、类型检查、lint、格式检查、build、e2e 和 1,000 赛季平衡命令。
7. 通过后提交独立保存点，再进入下一个模块。

## 风险与取舍

- 只增加更多文本变体的成本最低，但无法形成真正连续的职业事件；本模块选择故事图谱作为最小连续性基础。
- 先接 AI 会带来不可复现、越权改状态和内容审核风险；本模块先用作者可控内容建立确定性边界，未来 AI 只能在边界内润色已选中的文本。
- 故事链过长会拖慢月节奏；首批链限制为 2–4 个节点，并要求每月最多生成有限数量的主要事件。

## 自检结论

- 与 v3 月度流程兼容，没有引入玩家侧周推进。
- 效果和阶段转移仍由已有 simulation/application 机制控制。
- 所有新增持久化状态都有明确恢复点。
- 首批内容能直接验证用户关心的“选择后的具体反馈”，而不是继续显示统一的“现场结果”。
