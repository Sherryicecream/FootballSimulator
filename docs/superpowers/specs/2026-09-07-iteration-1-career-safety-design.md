# Iteration 1：生涯闭环与存档安全设计

> 状态：用户已确认范围，等待设计文档复核。
>
> 日期：2026-09-07
>
> 前置：M11 模块 1–3 已完成；当前进入体验优化阶段。本轮只实施 Iteration 1，Iteration 2–4 暂缓。

## 1. 背景与问题

现有游戏已经能够从青训推进至职业期和退役，但首次玩家仍可能遇到三类破坏信任的问题：

1. 最后一个青训年龄窗口结束但未达到毕业资格时，休赛期页面没有可执行的下一步，生涯无法继续，也无法正式结束。
2. Web 启动时只恢复存档列表中的第一个槽位；创建“新生涯”会删除当前档案；保存调用没有等待成功便更新界面，失败时可能造成“画面已推进、磁盘未保存”的错觉。
3. 事件反馈的“下一幕线索”区域对比度不足并残留 `NEXT` 英文，直接影响阅读。

Iteration 1 的核心不是增加内容或调整平衡，而是保证任何生涯都能安全继续、保存或结束。玩家必须能够信任不可回退自动存档，失败生涯也必须得到明确且有尊严的终局。

## 2. 目标

### 2.1 玩家目标

- 每种青训结果都有合法下一步或明确终局，不出现无操作页面。
- 玩家可以在允许的休赛期主动结束职业生涯，并在确认后查看回顾。
- 玩家能够查看、继续、创建和删除多段本地生涯；新建生涯不再静默删除旧档。
- 每次推进、选择、签约或终局操作只有在存储成功后才更新玩家所见状态。
- 玩家能看见简洁的“正在保存 / 已自动保存 / 保存失败”反馈。
- 下一幕线索在桌面、手机和文本缩放场景下清晰且中文一致。

### 2.2 系统目标

- 生涯终局由 application 用例创建，web 不直接修改 `careerPhase`。
- 终局原因、结束日期和账本证据能够持久化、迁移和用于回顾。
- 保存失败不消耗随机序列，不覆盖当前内存状态，也不清除待决事件。
- 单个损坏存档不影响其他档案的发现与加载。
- 现有 v1–v5 存档可迁移至新结构；已提交机械结果保持不变。

## 3. 方案选择

### 3.1 采用：最小可靠闭环

本轮保留现有 localStorage 多键存储方式，在其上完成：

- 版本化终局数据；
- 应用层终局用例；
- 等待持久化成功后再提交界面状态；
- 多生涯档案入口；
- 明确删除确认和损坏档案隔离；
- 已确认的对比度与中文问题修复。

优点是变更范围可控，能够直接解决玩家卡死和丢档风险，不阻塞后续体验迭代。局限是 localStorage 容量与事务能力仍有限；本轮通过可靠错误处理降低风险，不声称已经实现 IndexedDB。

### 3.2 不采用：只修界面症状

只增加未毕业按钮、删除确认和颜色修复，无法解决保存未完成便切换界面、存档选择缺失和终局缺少领域事实的问题，因此不采用。

### 3.3 不采用：本轮迁移 IndexedDB/Dexie

完整迁移会同时引入数据库版本、事务、导入导出和兼容适配器等独立工程，显著扩大 Iteration 1。它应在真实存档规模或容量证据表明 localStorage 不足时单独设计，不与流程止血混合。

## 4. 生涯终局模型

### 4.1 存档版本

Iteration 1 将生涯存档升级为 v6。v6 在 v5 基础上新增可空的 `careerEnd`：

- `kind`：`youth-no-contract`、`voluntary-retirement` 或 `market-exit`；
- `endedOn`：ISO 日期；
- `summary`：用于稳定回顾的作者化终局摘要；
- `evidenceIds`：支撑终局的账本事实 ID。

`careerPhase: 'retired'` 继续作为统一机械终态，表示球员生涯已经结束；界面根据 `careerEnd.kind` 显示“青训生涯结束”“主动退役”或“离开职业足坛”，不得把未毕业球员描述为正常职业退役。

旧 v5 的 `careerPhase: 'retired'` 迁移为 `careerEnd.kind: 'voluntary-retirement'`，结束日期使用既有 `retiredOn`，摘要由固定本地模板生成。非终态旧档迁移后 `careerEnd` 为 null。v1–v4 继续先走现有迁移链，再补 v6 字段。

### 4.2 合法终局

#### 最终青训窗口未毕业

条件：

- 已进入 `offseason`；
- `canContinueYouthSeason(save) === false`；
- `offseason.graduationEligible === false`；
- 没有待决事件或待确认反馈。

玩家只可选择“结束青训生涯并查看回顾”，经过一次确认后调用 application 终局用例。用例追加一条唯一账本事实，设置 `careerEnd`、`retiredOn` 和统一终态。重复提交保持幂等。

#### 主动提前退役

条件：

- 当前为 `pro-offseason` 或 `free-agent`；
- 没有待决事件或待确认反馈。

取消现有 30 岁硬门槛。退役仍只能发生在职业休赛期或自由球员窗口，不能在职业赛季进行中直接终止。界面必须进行一次简短确认，说明操作不可回退。

#### 长期市场退出

自由球员没有报价时继续保留“等待下一个窗口”和“结束职业生涯”两种选择。玩家主动选择结束时使用 `market-exit`；系统本轮不会根据等待次数自动强制退役。

### 4.3 回顾兼容

`buildCareerReview` 必须接受没有职业合同、职业赛季、俱乐部履历或国家队记录的终局存档：

- 总览使用青训出场、成长、关系和故事事实；
- 不适用的职业数据使用明确空态，不补造经历；
- 八维评价继续生成，但无证据的维度为低分或空档说明；
- 回放至少包含开局、青训机构、重要选择、赛季结局和终局；
- 幕后档案继续揭示潜力兑现和隐藏特质。

本轮不重新设计八维公式，只保证非职业终局可合法生成和渲染。

## 5. 可靠保存流程

### 5.1 单次提交顺序

所有会改变 `CareerSave` 的 Web 操作统一经过一个异步提交入口：

1. 读取当前已提交存档；
2. 调用 application 用例计算候选存档；
3. 将候选存档迁移并校验为 v6；
4. 设置保存状态为 `saving` 并锁定相关操作；
5. 等待存储适配器成功写入；
6. 写入成功后更新 React 中的 save、report 和 step；
7. 设置状态为 `saved`；
8. 写入失败时保留原 save、report、step 和待决节点，设置状态为 `error`，允许玩家重试。

候选存档只能计算一次并用于本次写入；失败重试可以重新从原存档调用确定性用例，但不得基于未提交候选继续推进。事件选择、随机位置和反馈因此不会被重复消耗。

### 5.2 保存状态

Web 使用三种玩家可见状态：

- `saving`：正在保存，不允许重复提交；
- `saved`：已自动保存，低干扰展示；
- `error`：保存失败，显示原因和“重试”操作。

读取、解析或迁移失败与写入失败分开呈现。错误文案不展示原始存档内容或敏感环境信息。

### 5.3 删除流程

删除是单独的不可逆存储操作：

- 玩家先选择具体档案；
- 确认框显示球员姓名与当前阶段；
- 等待删除成功后才从列表移除；
- 删除失败时档案仍保留在列表并显示错误；
- “创建新生涯”不调用删除。

## 6. 多生涯档案入口

### 6.1 启动行为

- 没有存档：直接进入创建页。
- 存在一个或多个存档：进入“生涯档案”页，不自动选择 localStorage 枚举中的第一项。
- 玩家可继续某段生涯或创建新生涯。
- 从进行中的生涯点击“生涯档案”返回列表，不删除当前档案。

### 6.2 档案摘要

每个有效档案展示：

- 球员姓名；
- 年龄；
- 青训机构、当前参赛俱乐部或终局标签；
- 生涯阶段；
- 当前日期；
- 最后保存时间；
- “继续”或“查看回顾”；
- “删除”次要操作。

摘要只从已校验存档和存档包装的 `savedAt` 派生，不向 save schema 复制展示字段。

### 6.3 损坏档案

损坏档案以独立卡片展示：

- 标明无法读取；
- 显示安全的失败原因；
- 允许确认后删除；
- 不尝试自动修复，不静默覆盖；
- 不阻止其他有效档案加载。

本轮不提供导出诊断包、云同步、跨设备同步或手动回档。

## 7. Web 流程边界

`App.tsx` 继续负责页面装配，但不得新增领域判断散落在事件处理器中：

- application 提供终局资格和提交用例；
- persistence 适配器提供列举摘要所需的带状态读取结果；
- 新的 `CareerSaveSelector` 只展示档案、发出继续/创建/删除意图；
- 新的保存状态组件只展示提交状态；
- 现有 dashboard 的“新生涯”改为“生涯档案”，不再直接删除；
- `CareerReviewPage` 的“开始新生涯”创建新档，不删除已结束档案。

为控制风险，本轮只提取支撑可靠提交和档案入口所需的小型职责，不重写整个 `App.tsx`，不引入新的全局状态管理框架。

## 8. 可读性修复

“下一幕线索”使用现有设计令牌建立稳定的前景色、背景色和边框组合：

- 标题、正文和次要文字不能只靠透明度与浅色背景区分；
- `NEXT` 改为“下一幕”；
- 同一事件反馈路径不再出现未设计的英文状态标签；
- 320px 宽度和 200% 文本缩放下正常换行；
- 信息意义不能只依赖颜色。

本轮只修复已确认的事件反馈可读性，不统一全站按钮圆角，不新增插图，不重新设计月报。

## 9. 错误处理与兼容性

- v1–v5 合法存档必须能够加载为 v6。
- 迁移不能重新生成比赛、事件、报价、关系或随机结果。
- 单槽迁移失败只标记该档案为损坏。
- localStorage 空间不足或浏览器拒绝写入时，界面保持原状态。
- 待决事件保存失败后仍显示相同事件和相同选项。
- 事件结果保存失败后不能展示未持久化反馈。
- 删除失败不移除档案卡片。
- 已终局存档加载后直接进入回顾，不进入可推进仪表盘。
- 未完成的创建表单和尚未选择青训机构的临时开局不作为正式生涯档案保存；正式档案从青训机构选择完成后建立。

## 10. 实施拆分

任务必须顺序执行，每项形成独立可测试结果：

1. **终局契约与迁移**：新增 v6、`careerEnd`、迁移和契约测试。
2. **终局应用用例**：实现未毕业终局、主动退役、市场退出及幂等账本事实。
3. **非职业回顾兼容**：确保青训终局能够生成并展示回顾。
4. **可靠保存提交**：统一候选存档校验、等待写入、成功后切页和失败重试。
5. **多生涯档案**：实现有效/损坏档案列表、继续、新建和确认删除。
6. **Web 终局接线**：消除无操作休赛期，接入提前退役确认和档案返回。
7. **事件反馈可读性**：修复对比度、中文和响应式文本。
8. **整体验证与文档收口**：通过完整门禁、1,000 生涯平衡并更新产品基线与路线图。

## 11. 验收标准

### 11.1 功能

- 最终青训窗口未毕业时存在明确终局操作，完成后进入有效回顾。
- `pro-offseason` 和 `free-agent` 可以主动结束生涯，职业赛季进行中不提供此操作。
- 终局均需一次确认，取消确认不会改变存档。
- 终局后不能推进、签约或重新抽取事件。
- 新建生涯不删除任何既有档案。
- 玩家可以列出并继续多段有效生涯。
- 删除指定档案需要确认且不影响其他档案。
- 保存成功前页面不进入候选状态；保存失败保留原节点并可重试。
- 单个损坏档案不影响其他档案。
- 下一幕线索清晰可读且不再显示 `NEXT`。

### 11.2 玩家体验

- 玩家能够判断当前是否正在保存、已经保存或保存失败。
- 玩家不会在最终青训休赛期遇到无可用操作页面。
- 玩家能够理解青训失败、主动退役和市场退出是不同结局。
- 玩家能够安全创建第二段生涯并返回第一段生涯。
- 玩家无需费力辨认下一幕线索，并能在手机和文本缩放下完成反馈流程。

### 11.3 自动测试

- contracts：v6 schema、v1–v5 迁移、终局字段与非法组合。
- application：终局资格、阶段约束、幂等性、账本证据和随机位置不变。
- simulation：无职业数据的生涯回顾及既有职业回顾回归。
- persistence：多档列举、保存失败、删除失败、损坏档案隔离和 savedAt 排序。
- web：终局确认、档案页、保存状态、错误重试和事件反馈中文/可读性。
- E2E：未毕业终局、多生涯恢复、确认删除、提前退役、待决事件刷新、保存失败保持原页面。
- 完成前运行 `pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm format:check`、`pnpm build`、`pnpm test:e2e` 和 ROADMAP 指定的 1,000 生涯平衡命令。
- 平衡验收确认毕业率、承诺兑现率、国家队比例、伤病率和世界级比例无非预期漂移；新终局必须与职业退役分开统计。

## 12. 明确不包含

- 不修改青训或职业比赛数量、出场频率、赛程和比赛公式。
- 不修改成长速度、训练公式、位置权重、伤病概率、毕业门槛或报价平衡。
- 不调整事件数量、权重、选择判定、月度节奏或随机序列语义。
- 不增加周推进、普通快进或自动完成赛季。
- 不压缩月报，不重做属性展示，不解释位置深度图。
- 不新增经典比赛、高燃瞬间、生涯回忆墙或剧情图鉴解锁变化。
- 不新增俱乐部特色、事件、故事线、插图或 AI 能力。
- 不统一全站按钮样式，不进行整体视觉改版。
- 不迁移 IndexedDB/Dexie，不实现云存档、导入导出或诊断包。
- 不重写 `App.tsx`、职业流程或存档迁移体系，不引入新的状态管理框架。
- 不实施 Iteration 2、Iteration 3 或 Iteration 4 的任何内容。

## 13. 完成定义

Iteration 1 只有同时满足以下条件才可关闭：

1. 所有玩家生涯都能继续或正常结束。
2. 多段生涯能够保留、选择和安全删除。
3. 所有关键状态变化以存储成功为提交点。
4. 保存失败不会造成画面与持久化状态分叉。
5. 旧存档可迁移，终局可回顾，随机结果不重投。
6. 下一幕线索清晰且中文一致。
7. 全部仓库门禁与 1,000 生涯平衡验收通过。
8. Iteration 2–4 的内容没有混入本轮。
